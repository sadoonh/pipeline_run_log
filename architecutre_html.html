03 / Business definitions

Same business rules. Two homes.

Data definitions, metrics, dimensions, and table relationships. Example: completed revenue by customer region.

01 / Databricks Genie

Unity Catalog metric views

Defined in YAML. Published in Databricks. Queried by Genie.

version: "1.1"
source: analytics.sales.orders
comment: Order revenue in USD
joins:
  - name: customers
    source: analytics.sales.customers
    'on': source.customer_id = customers.customer_id
dimensions:
  - name: Customer region
    expr: customers.region
measures:
  - name: Completed revenue
    expr: >-
      SUM(CASE WHEN source.status = 'completed'
          THEN source.amount ELSE 0 END)
02 / NEWT + NeeAI

Business-definitions YAML

Loaded by NEWT. Supplied as context to NeeAI.

data_definitions:
  orders: {table: public.orders, grain: one row per order}
  customers: {table: public.customers, grain: one row per customer}
  amount: {column: orders.amount, meaning: Order value in USD}
metrics:
  completed_revenue:
    sql: >-
      SUM(CASE WHEN orders.status = 'completed'
          THEN orders.amount ELSE 0 END)
dimensions:
  customer_region: {sql: customers.region}
table_relationships:
  orders_to_customers:
    join: orders.customer_id = customers.customer_id
    cardinality: many_to_one
    join_type: left
04 / Trade-offs

Less workflow code or more control?

Both reuse NEWT. The main choice is a managed Genie workflow versus a custom NeeAI workflow.

Key difference01 Databricks Genie02 NeeAI
DataMigrated Databricks tables, governed by Unity Catalog.Existing RDS, through NEWT’s connection.
DefinitionsUnity Catalog metric views.YAML: data, metrics, dimensions, relationships.
Main gainLess custom workflow code.Genie handles question → SQL → answer.More control.We control SQL checks and the answer workflow.
Main trade-offPlatform setup; less control over query steps.More code to build and maintain.
